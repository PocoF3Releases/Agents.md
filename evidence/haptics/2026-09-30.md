## Objective results

  expected duration and one completion callback each.
- Double click: 120 ms total, two pulses. Remaining durations 20 ms except POP 28 ms.
- Amplitude, cancellation, invalid arguments, extended-ID rejection and a
  65536 ms request accepted then cancelled passed.
- Rootless framework playback completed for all seven predefined effects and
  an amplitude waveform; cancellation left IDLE. Shell `feedback` attempts
  rejected as `ignored_background` were not counted as playback successes.
- Candidate compiled/linked for Android and passed host worker/mapping/gain,
  callback/reentry, failure, cancellation and amplitude-isolation checks.
- Both ran as UID system in `hal_vibrator_default`; SELinux remained enforcing.
  Candidate remained stable with no service log errors during final observations.
- Foreground Tremor feedback completed after the correction. Android's haptic
  intensity settings were MEDIUM. Cached resonance was 177.7 Hz.
- Live DTS: drive 73/73; RAM/RTP/default boost 17 (`0x11`); battery compensation 1.
  Stock compensation and strength code differed only in logging, not arithmetic.

## Root cause and acceptance

The old implementation used native fallback gains 30/64/128 and a half-strength
RAM-2 texture tick. Alioth actually enables the MIUI per-effect intensity path:
`VibrateUtils` sends 0.375/0.625/1.0, the extension stores each factor, and
`InputFFDevice::playEffect` applies it with global intensity initialized to 1.0.
The correction selects gains 48/80/128 and mesh-light RAM 5 without double attenuation.

The maintainer reported previously weak effects improved and were acceptable,
though softer than HyperOS. This supports the correction; it does not establish
measured acceleration, uniform perceptual strength or full stock parity. Kernel
stock values were retained rather than raising the floor for every waveform.

## Temporary deployment and recovery

The accepted candidate was mounted over
`/vendor/bin/hw/android.hardware.vibrator-service.xiaomi_aw8697` from an isolated
`/dev/aw8697-validation` tmpfs in the init mount namespace, with executable label
`hal_vibrator_default_exec`. It disappears on reboot; the next ROM rebuild must
include the final source commit. Do not assume it remains mounted in a new chat.

Directly binding a `/data/local/tmp` executable failed on the nosuid source mount.
The original service was restored before switching to tmpfs. No SELinux exception
or global data-mount change was made. A test-client vendor-first LD_LIBRARY_PATH
also broke Binder lookup; system libraries plus its local test dependency worked.
These setup failures were not production HAL playback failures.

Rollback of that exact temporary deployment, only after confirming it is present:

```sh
# Root, init mount namespace; never run blindly on a different setup.
stop vendor.aw8697.vibrator
umount /vendor/bin/hw/android.hardware.vibrator-service.xiaomi_aw8697
start vendor.aw8697.vibrator
umount /dev/aw8697-validation
rmdir /dev/aw8697-validation
```

Verbose evidence and recovery bundles were kept privately under
`~/evo17/out/haptics-rebuilt-validation-20260930-013650` and
`~/evo17/out/haptics-production-review-20260930`. They are not required to read
this conclusion. Tracked production test/research files were removed as requested;

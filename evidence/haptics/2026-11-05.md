## Pixel and HyperOS comparison

**Source/reverse-engineering checked:** inspected pinned Pixel
[gs101](https://android.googlesource.com/device/google/gs101/+/fd8ae4af90419640564fd8dd73dfbc255bb881a0/overlay/frameworks/base/core/res/res/values/config.xml)
and [gs201](https://android.googlesource.com/device/google/gs201/+/0e10376c1e2dcb98ba8efcf1f10406f18b62d2f3/overlay/frameworks/base/core/res/res/values/config.xml)
common configuration files do not override these legacy arrays. Their intensity
policy is separate. The older public
[Felix CS40L26 HAL](https://android.googlesource.com/device/google/felix/+/1226602095ff6fec9c80888dd1caf98e39e03bcb/vibrator/cs40l26/Vibrator.cpp)
uses per-effect voltage endpoints and actuator calibration. Its numeric gains,
audio-haptic caps and conditional capabilities cannot establish AW8697 tuning.
These sources are references, not measurements of a current Pixel device.

HyperOS framework-res uses clock fallback 0, 10; its standard caller also uses
OFF/ON timings. The existing 30 ms Alioth pulse was retained to avoid unrelated
retuning. Stock long-press/virtual-key arrays differ, but normal MIUI linear-motor
feedback prioritizes sys.haptic event/strength pairs and its vendor extension.
For example CLOCK_TICK maps mesh.light to effect 5, strength code 1 (0.625), not
an AOSP timing waveform. Copying such pairs into AOSP arrays would be incorrect.
JADX numeric resource IDs were checked against the actual stock resource table
because its automatic R-name substitution was unreliable.

Stock input SHA-256: framework-res.apk
`8c5ee41b52e475116e2eb2f44d02910a724844517f62c196ce10bdec4e55bca8`;
vibratorfeature service
`9cbc970e2cd3b2531d26d38bbba5abdd0f3a6874d1603e6f1d5e8c8aa8c7409d`.
Native strength/extension behavior reuses the matching

## Verification and limits

**Host-tested:** the immediate-onset resource assertion fails for 125, 30 and
passes for 0, 30; ON duration and every other resource entry remain identical.
**Build-tested:** `lunch lineage_alioth-cp2a-user` and
`m -j4 FrameworkResOverlayCommon android.hardware.vibrator-service.xiaomi_aw8697 VtsHalVibratorTargetTest`
pass. Compiled RRO inspection confirms `[0, 30]`; the tested HAL and VTS binaries
are byte-identical before/after this build.
The six other previously consolidated source trees remain identical to the
[final implementation review](../final-implementations-20261105.md); common's
only new production delta is this resource value. Canonical recovery patches
reapply and `--check` pass without changes to their contents.

**Device-tested, installed production HAL:** 15 selected vibrator VTS cases pass:
preemptive off, timed/effect callbacks, seven effects/all strengths, invalid
values, amplitude changes, primitives/durations, composition bounds and actual
nonempty composition callbacks, plus resonance. Four private callback tests each
ran five iterations: cancellation, delay cancellation, replacement, completion
then repeated off. All 20 sequences pass with exactly-once callbacks.

The HAL runs as system in hal_vibrator_default with SELinux Enforcing. All eight
HAL/library/waveform/firmware hashes match the built artifacts. HAL SHA-256:
`1e4fc25a2fd8d552c6491e19d76484426bfb88083156e512e2870bf88a0939a0`.
Custom-wave ABI 2, tagged gain ABI 1 and cached resonance 176.9 Hz were observed;
no calibration-triggering f0 read was used. Playback was idle afterward and all
temporary test files were removed. No service override, settings change, reboot
or flash was needed. These tests cover the existing native HAL, not the new,
uninstalled fallback overlay.

The [known scale-zero minimum-strength defect](2026-11-02.md#demonstrated-remaining-scale-zero-defect)
remains: Pixel's calibrated minimum does not supply a safe AW8697 value. No
guessed gain floor was added. Exact perceptual parity, a calibrated minimum,
full RichTap/PWLE and a fresh complete ROM acceptance matrix remain unproven.
No new test or documentation files enter production source repositories.
